# 键盘快捷键：三层模型与三条纪律

一个键归谁，看它在哪一层。**认领顺序是从下往上**：焦点区先答，屏幕后答，应用层最后。

| 层 | 何时生效 | 注册在哪 | 例子 |
|---|---|---|---|
| **L0 应用** | 本窗口最前、当前路由最前、非移动平台 | `main.dart` 的 `HardwareKeyboard` handler | `⌘1…8` · `⌘/` · `⌘,` |
| **L1 屏幕** | 该屏最前，**且文本框没拿着键盘** | 屏幕根部的 `Focus.onKeyEvent` | `⌘F` · `F5`/`⌘R` · `⌘\` · `⇧⌘\` · `⌘⌥1…5` |
| **L2 焦点区** | 该区是当前活动区 | 每区一个 `FocusPane` | 选区类全部：`Enter` · `F2` · `Delete` · `⌘A` · `Esc` |

一张表：[`lib/core/app_shortcuts.dart`](../../lib/core/app_shortcuts.dart)。
绑定、发现性（`⌘/` 面板 / 菜单 trailing / 设置页「键盘快捷键」）和测试三处**只能**
从它读，平台差异也只在它里面解决。

---

## 纪律一 · 选区类的键归 L2，不归 L1

这一条是本轮存在的理由。此前目录树在 L2 认领 `Delete`（每行一个 `FocusNode`），
文件网格的 `Delete` 却在 L1——同一个动作分居两层，**谁先拿到焦点谁赢**。而文件卡是
`Listener`+`GestureDetector`，根本不可获焦，所以点过一次文件夹之后，
`Delete` 与 `F2` 就永远属于那个文件夹了：在网格里选三个文件按 `Delete`，弹出来的是
「移除文件夹？」，选区纹丝不动。点回网格也要不回来。

修法不是给文件卡加判断，而是让「谁答这个键」只有一个答案：

- 每个可以拥有键盘的区是一个 [`FocusPane`](../../lib/widgets/ui/focus_pane.dart)：
  浏览器的 `tree` / `grid` / `staging`，工作台的画廊。
- **一区一个节点，不是一张卡一个**。几百个 `FocusNode` 既费内存又污染 Tab 遍历；
  唯一需要按卡获焦的功能是方向键导航，那是第二期。
- 点区内任意位置即取焦——但**仅当区内没人拿着焦点时**，否则点到树的行内改名框会把
  焦点从它手里抢走，而那个编辑框失焦即提交。
- 「没有活动区」是合法状态（刚进屏、点了工具栏）。此时 L2 一个键都不认领，L1 照常。
  但也不要让它成为**默认**状态：每屏给一个区 `autofocus`，否则 `⌘A` 这种进屏第一个
  合理动作要先点一下才有。

**活动区必须看得见**，否则「Delete 删什么」还是只能靠试。两个记号，一强一弱：
选中项在活动区里是强调色底 + 描边，不在活动区里降成中性（选区还在，只是不听键盘），
这是主要的那个；活动区顶边 2px 强调色，负责回答「还没选任何东西时键盘在谁那」。

## 纪律二 · L1 认领任何键之前先过 `isTextEditingFocused()`，没有例外

一个文本框**没吃掉**的键仍会上浮到每一个祖先 handler，而屏级 handler 位于
`DefaultTextEditingShortcuts` **之下**——所以 L1 抢走就等于字段永远收不到。

`⌘F` 与 `F5` 曾经写在闸门上面。后果不是「搜索框没反应」，而是：在目录树里改名改到
一半按 `⌘F`，焦点跳去搜索框，而行内编辑器**失焦即提交**
（`folder_name_editor._onFocusChange` → `_submit(fromBlur: true)`），半截的名字就这么
落了盘。闸门之上只允许放「与文本无关且必须随时可用」的键——目前一条也没有。

（用**鼠标**点到别的区确实会提交，那是 `FolderNameEditor` 明文的契约，也是所有文件
管理器的习惯。纪律二管的是按键。）

## 纪律三 · L0 只放不依赖任何选区、任何屏幕状态的键

`⌘1…8`、`⌘,`、`⌘/` 合格。`⌘/` 是唯一一个允许在自己已经打开时再触发的 L0 键——
它得能把自己关掉。

## 会静默失效的几处

- **屏级 handler 必须始终是「持有键盘的那个节点」的祖先**。按键只从主焦点往上冒，
  所以一旦焦点掉到 handler 之外，整屏的键就全部失灵，直到用户再点一下。
  两屏的处境不同，别照抄：
  - 文件浏览器的网格区**永远挂着**，关掉暂存栏时焦点会退回它（`Focus` 卸载会把焦点还给
    scope 里上一个拿过的孩子），所以那里的 handler 是普通 `Focus` 就够——
    `browser_shortcut_scope_test` 的「区没了之后屏幕还认键」钉住这条。
  - 工作台切到对比器标签会把画廊**连同它的焦点区整个卸载**，退无可退，于是屏幕级的键
    全死。那里的 handler 因此挂在 `FocusScope` 上（`workbench_layout.dart`），
    焦点回落到它自己身上。
- **修饰键匹配是精确的**：`⇧⌘1` 不是 `⌘1`。这是 `⌘⌥1…5` 能与 `⌘1…8` 共存的前提，
  也顺手挡掉了德语布局上 AltGr（= Ctrl+Alt）误触 `Ctrl+2`。代价是任何和弦都必须
  **显式登记**：`⌘⌫`（Finder 的移到废纸篓）就是因此差点被匹配规则抹掉的，现在以
  `macOSOnly` 登记；Windows 的 `⇧Delete` 故意不绑——那边它的意思是「跳过回收站」，
  而本应用把这个选择放在确认框里。
- **`Delete` 与 `⌫` 永远成对**：macOS 键盘主区那颗是 `⌫`。
- **同一个 scope 内不得有两条同 activator**，跨 scope 可以：`Esc` 在 L1 退出搜索、
  在 L2 清空选区，这是 `Esc` 阶梯（浮层 → 搜索 → 选区 → 不处理），不是冲突。
  `test/app_shortcuts_test.dart` 两个平台各跑一遍钉住这条——**它曾经是恒真的**：
  用 `SingleActivator` 当 map 的键，而那个类没有值相等，于是查表永远 miss。
- **活动区的认领要按身份放，不能按名字放**。两屏的中间区都叫 `ShortcutPane.grid`，
  切屏时新的那个先挂载认领、旧的后 dispose，按名字比较就会把新的认领误清掉。
- **`FocusPane.activeOf` 的依赖不随重建清空**（`Element._dependencies` 只在
  deactivate 时清）。所以只让**正在画选中态**的行与卡去问它：从未被选中过的卡不登记，
  这才是让开销与选区成正比的那一半。
- **`⌘/` 面板读活动区要在打开的那一刻读**。打开面板本身会把键盘拿走，等面板 build
  时各区都已经如实放手了——用户问的是按键那一刻是哪块在听。

## 平台拼法

macOS 把一个和弦写成一串符号（`⇧⌘C`），Windows / Linux 逐键用 `+` 连
（`Ctrl + Shift + C`）。触发键一律用**词**（Enter / Delete / Backspace / Esc）而不是
`↩ ⌦ ⌫`：那些字形缺字体的太多，画成豆腐块的快捷键什么也没教会人。修饰键保留符号。
唯一在表外的修饰键是拖拽复制（`AppCopyModifier`，macOS `⌥` / 其余 `Ctrl`）——
那是平台的拖放约定，没有按下动作，不进面板。

## 移动平台

一律不注册（`AppShortcuts.registersShortcuts`）：手机没有物理键盘可注册，文件浏览器
整屏是受限页。设置页的「键盘快捷键」一类在移动平台**整类不出现**，不是灰掉——
不能生效的设置比没有更糟，它会引出「那怎么打开」这个问题。外接键盘的 iPad 留到第二期，
届时要单独想「没有 `⌘` 修饰键的物理键盘」。
