# 30 · 知识吸收协议：新事实怎么进来、旧结论怎么改、什么时候过期

本库的价值在于「已验证」三个字。一条没有证据的事实混进来，比没有这条事实更糟——审查时会据此判错。本篇规定：一条新事实（新平台、新模型、新结论）从哪进来、写到哪、怎么写、怎么推翻旧的、怎么过期，以及每次写回的自检清单。

两个原则贯穿全篇：

1. **事实只有一处正文，其余都是指针。** 正文在 0x / 1x 主题篇（02–06、13、14、16）；20 系列矩阵是结论表（20 §0 与 §3 各节的「正文所在」行兼作目录），只写结论 + 指针。改事实 = 改正文一处 + 同步所有指向它的结论格。
2. **改结论必须留痕，删除只发生在「待核实」表。** 旧结论被推翻时不删旧句，写「旧 → 新（日期，被哪次实测推翻）」。唯一允许删行的地方是 31 篇：核实完成后从那里删。

## 1 一条事实的最小单元

写回的每条事实都要能拆成这七个字段，缺一个就还不是「事实」，是线索：

| 字段 | 例 | 缺了会怎样 |
| --- | --- | --- |
| **主键** (平台·渠道·线路, 面, 模型) | (New API · `[Pro]`, ②, gpt-5.6-sol) | 无法和别的行区分；中转站上同一 id 不同渠道结论相反 |
| **发了什么** 字段名与值 | `text.format:{type:"json_schema", strict:true, …}` | 后人无法复现 |
| **看到什么** 状态码 / 回显 / 回包字段 / 计费数字 | 200，回显 `{type:"text"}`，答案是合法 JSON 但不受 schema 约束 | 「支持 X」三个字审查时用不上 |
| **结论记号** ✅ ❌ 🔇 🔀 📄 | 🔇（收下不生效） | 静默 / 会响是审查优先级的依据 |
| **不这样会怎样** | 调用方拿到能解析的 JSON 却以为 schema 生效了 | 读者不知道严重程度 |
| **证据** 记法 + 日期 + 样本量 | 【实测 2026-09-24】4/4 | 半年过期规则无法执行 |
| **出处** 主题篇小节 | 04 §5.1 | 矩阵格子指不回正文 |

只有「发了什么 / 看到什么」两项能从日志里直接抄；其余五项是人判断的，写的时候要意识到这一点。

## 2 进来的四种入口

| 入口 | 典型场景 | 证据等级上限 | 进库前必须做的事 |
| --- | --- | --- | --- |
| **A 付费实测** | 拿到新 key，按 06 §8 纪律打请求 | 【实测 YYYY-MM-DD】 | 记样本量；流式 / 非流式各测；中转站至少测两个渠道（06 §8 第 7–11 条） |
| **B 审查项目时发现** | 审别人的代码，它在真实服务上这样写且能跑 | 【实现】 | 写清是哪个项目、哪条路径；判错前先实测（SKILL.md 证据记法） |
| **C 读文档 / 读中继源码** | 官方 API 参考页、New API 仓库 | 【文档 YYYY-MM】/【中继源码】 | 记页面日期；与已有实测冲突时两者并记、实测优先 |
| **D 用户口述 / 对话中的说法** | 「我试过 X 在 Y 上不行」 | ⚠ | 只能进 31 篇待核实表，不能进正文与矩阵 |

判断入口时别高估：从网关翻译层看到的回包，对官方只算「经 X 的实测」，且只有回包原样的面才能记成官方事实（01 §9.5 透传证据清单）。请求侧被重新序列化的网关，「发 X 会不会 400」只对这台网关成立。

## 3 放到哪：决策树

按顺序问，第一个「是」就停：

```
这条事实是关于……
├─ 一个尚未核实的疑问 / 只有口述 / 只有 ⚠ ──────────────→ 31-open-questions（只进这里）
├─ 出图 / 视频 / ASR 的 route、尺寸、计费、时间码 ──────→ 正文：13 / 14 / 16 对应小节
│                                                          结论格：23-media-matrix
├─ 某个平台本身（地址、鉴权、目录、注入、改写、报价）──→ 正文：20 §3 该平台节（平台级事实的家；探测 / usage 口径的通用规则在 06）
│                                                          结论格：20 §2 主表；该节开头「正文所在」行列出它在别篇的小节
│                                                          （只有新的分层教训才进 01 §9）
├─ 某模型在某平台某面上的行为（思考 / 结构化 / 工具 /
│  服务端工具 / 多模态 / 上限）──────────────────────────→ 正文：03 / 04 / 05 / 02 对应小节
│                                                          结论格：22-model-capability-matrix 该家族节
│                                                          （服务端工具另加 22 §14 专表一行）
├─ 协议族通用（与厂商无关的 wire 形状、事件、字段）────→ 正文：02–06 对应小节
│                                                          结论格：02 §1 总对照表（四族 × 功能维度）；非对话面见 02 §1.1
├─ 以「现象」形式出现的静默失败（看起来成功其实失败）─→ 11-pitfalls 追加，编号接着排，不重排
│                                                          并在相关矩阵行的「坑」列补编号
└─ 架构设计经验（分层、裁决、测试设计）─────────────────→ 01 对应小节；若是配方性质进 12
```

三条补充规则：

- **一条事实常常同时命中两层**（例：`[Pro]` 丢 `text.format` 既是平台行为也是模型 × 平台行为）。正文只写一处（选最靠近原因的：转换层 / 渠道行为 → 20 §3 该渠道节；模型自身行为 → 03/04/05），矩阵两张表各一格，都指回同一处正文。
- **新平台**：20 §2 加一行 + §3 加一节（节首写「正文所在」行）→ 01 §9 加数据行样例（可选，只在它有新的分层教训时）→ 逐个模型进 22 → 有媒体面进 23。
- **新模型（老平台）**：22 该家族节加行；若家族不存在，新建节（含「家族固有特性」列表，第一版只写文档口径 📄 + 已测的平台行）。

## 4 写法与模板

### 4.1 正文条目（主题篇）

```
**<一句话结论>**（<平台·渠道>，<面>，<模型>，【实测 YYYY-MM-DD】<样本量>）。
发 `<字段>: <值>` → <状态码>，<回包 / 回显关键字段>。
不这样会怎样：<静默后果或账单后果>。
对策：<代码侧 / 数据侧各一句>。
```

例：

> **`[Pro]` 档整个丢 `text.format`**（New API · `[Pro]`，②，gpt-5.6-sol，【实测 2026-09-24】省略 strict 4/4、显式 strict 4/4）。发 `text.format:{type:"json_schema",…}` → 200，回显 `{type:"text"}`，答案仍是合法 JSON。不这样会怎样：能解析的 JSON 让调用方以为 schema 生效，字段缺失 / 枚举越界要到下游才炸。对策：画像格 `structuredOutput` 只对该上游写 `false`；代码侧不加中转站分支。

### 4.2 矩阵格子

格式：`<记号> <关键值>（<补充>）`，每格只写记号 + 关键值 + 证据 + 指针，原因与报文在正文；装不下就写结论 + 指针。

- 思考控制格：`✅ 真分档（low 295 / xhigh 588 tok）；none 🔇 回显 medium`
- 服务端工具格：逐个工具，`web_search ✅ 真搜 6–10 s；code_interpreter ❌ 400；image_generation ❌ 403`
- 静默失败要点格：只写 🔇 与 🔀 的，会响的不写这里

### 4.3 待核实条目（31 篇）

```
| OQ-NNN | P? | 平台 | 面 | 模型 | 待核实：发 <什么>，看 <什么字段> | 现状：库里写「…」，证据【…】 | 相关篇章 | 来源 |
```

### 4.4 坑条目（11 篇）

沿用 11 篇现有格式：编号、现象、原因、对策、详见。编号只增不改。

## 5 修正旧结论

旧结论被新证据推翻时，四步：

1. **正文**：原句保留，前面加「旧：」，后接「→ 新：…（YYYY-MM-DD，被 <入口 / 样本> 推翻）」。不删旧句——审查旧项目时它解释「为什么当初这样写」。
2. **矩阵格**：同一格写「旧：… → 新：…」；格子放不下就只写新结论 + 「（旧结论见 NN §x）」。
3. **20 §3「正文所在」行 / 20 主表的证据列**：日期更新为新实测日期。
4. **31 待核实**：如果这条原本是 P5「文档与实测冲突未定论」，现在定论了 → 删行；如果推翻后产生新疑问（例：「只在这台复现，别台呢」）→ 加一行。

三种不算「推翻」、不用留痕改写的情况：

- **样本扩展**：同一结论多了一个平台 / 型号验证 → 直接在证据列追加日期与样本，结论句不动。
- **精度提升**：「约 $0.03 / 次」改成「按条 $0.014」→ 写「旧：… → 新：…」但可以在同一行内。
- **纯笔误**：字段名拼错、指针错 → 直接改。

## 6 过期与复核

- **半年规则**：证据日期距今超过 6 个月的事实，审查时按「待核实」对待（SKILL.md）。每次批量写回时顺手扫一遍：超期的在证据列尾加「⏳待复核」，并在 31 §4 加一行。
- **日期未标的实测**：一律视为超期（31 §4 已列出的：Ollama / LM Studio、Midjourney、ASR 专营六家）。
- **复核完成**：日期更新、去掉 ⏳、从 31 §4 删行。复核结果与旧结论不同 → 走 §5。
- **过期不等于错**：过期只降低证据等级，不改结论记号。审查报告里写「依据 2026-03 实测，已超期」。
- **平台下线 / 模型下线**：不删行，结论格写「❌ 已下线（YYYY-MM-DD 实测 404）」，证据更新；下一次大整理再移到「已下线」附录。

## 7 证据等级怎么定

| 你手里有的 | 记法 | 能不能据此判错 |
| --- | --- | --- |
| 自己发的请求 + 看到的响应（含日志） | 【实测 YYYY-MM-DD】 | 能 |
| 官方文档 / API 参考页 | 【文档 YYYY-MM】 | 不能；项目不一致时写「待核实」并给验证方法 |
| 读中转站 / 网关源码 | 【中继源码】 | 只对那一类中转站能 |
| 某项目代码在真实服务上跑过，本库没独立复核报文 | 【实现】 | 不能；当线索 |
| 推断、类比、文档含糊、用户口述 | ⚠ / 【未验】 | 不能 |

降级规则：经翻译层网关看到的官方行为 → 最高只能记「【实测 YYYY-MM-DD 经 X】」，且只有回包原样的面才能记为官方事实；请求被重新序列化的网关上「发非法值 200」不能推出官方也 200。

不要为了显得完整而升级证据。宁可一格 `—`，不要一格 📄 冒充 ✅。

## 8 写回自检清单

每次写回前逐条过：

- [ ] 七字段齐全（§1）：主键、发了什么、看到什么、记号、后果、证据 + 日期 + 样本量、出处。
- [ ] 正文只写了一处；矩阵格都指回这一处。
- [ ] 写回前 grep 过该主键（模型 id、平台名、字段名），没有另起重复条目；有旧条目的走 §5。
- [ ] 主键是 (平台·渠道·线路, 面, 模型)，中转站没有把渠道漏掉；同一台至少两个渠道都测了才归转换层（01 §9.2 第 2 条）。
- [ ] 记号用对：收下 200 但不生效是 🔇 不是 ✅；文档口径是 📄 不是 ✅。
- [ ] 数值、字段名、状态码、报错原文都在；没有「支持 X」这种空话。
- [ ] 静默的后果写了「不这样会怎样」。
- [ ] 新平台：20 加行加节；新模型：22 加行；新媒体面：23 加行；新现象：11 加编号（表格一行，原因写在正文篇）。
- [ ] 该删的只从 31 删；正文与矩阵不删行。
- [ ] 证据日期超半年的加了 ⏳ 并进 31 §4。
- [ ] 表格单元格内没有 `|`、没有换行。
- [ ] CHANGELOG.md 加一行：日期、入口类型、改了哪些文件、一句话。

## 9 三个吸收样例

**样例一：新平台（假设「某某云」，只有 ① 面，测了 3 个模型）**

1. 20 §2 加一行（面、base 与鉴权、目录形态、手脚、计费）；§3 加一节，逐条写：透传证据（回包是原样还是翻译层）、非法参数报法、注入读数、`/models` 可信度。
2. 22 各家族节按 (某某云, ①, 模型) 加行；服务端工具有的话 §14 加行。
3. 若它教了新的分层教训（例：又一种「同一 id 多渠道」），01 §9 加数据行样例；否则不加。
4. 没测的面（②③④）不写 ❌，写 `—`；想测但没 key 的进 31 P1。
5. CHANGELOG 一行。

**样例二：新模型（假设 Claude Opus 6，经 OrcaRouter ④ 原样测）**

1. 22 §4 Claude：「家族固有特性」只改跨平台成立的（如新代次的 thinking 方言）；平台表加一行 (OrcaRouter ④, Opus 6)。
2. 03 §2 / §3 正文：新方言或新档位写在对应小节，标「经 OrcaRouter 原样，【实测 YYYY-MM-DD】」。
3. 官方直连未测 → 22 该行「平台」列写「Anthropic 官方 · 经 OrcaRouter ④（回包原样）」，不写成「Anthropic 官方」。
4. 目录上限从网关目录抄的 → 标「网关目录，推断」（01 §9.5）。

**样例三：推翻旧结论（假设复测发现 `[Pro]` 又开始执行 `text.format`）**

1. 04 §5.1 正文：「旧：不论写不写都丢（2026-09-24）→ 新：执行（2026-11-02，4/4）；同一档位不同账号，按『当时当档』理解」。
2. 22 §3 GPT 表 `[Pro]` ② 行结构化格：同样写旧 → 新。
3. 20 §3 `[Pro]` 节的静默行为列表：该条改写并注日期。
4. 20 §3 New API 节「正文所在」行证据日期更新。
5. 31：若之前有「`[Pro]` 是否稳定丢 format」的 OQ → 删；新增「账号池同一档位是否随账号变化」的 OQ（若还没有）。
6. 11 篇坑 160 不改编号，条目正文加一句「2026-11-02 复测已不复现，见 04 §5.1」。
